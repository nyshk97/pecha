# Haasの音声認識への乗り換え

## 概要・やりたいこと

文字起こしを、OSの音声認識（`SpeechAnalyzer` + `SpeechTranscriber`）から、日本語の音声認識モデル **Haas-ja-v1.0**（Core ML・INT8。[okayuji/Haas-ja-v1.0-CoreML-INT8](https://huggingface.co/okayuji/Haas-ja-v1.0-CoreML-INT8)）に替える。

背景:
- Pechaは「KeyVoiceと同じOSの音声認識を使うので、精度も同じになる」という前提で作った（前のplanの「KeyVoiceの調査結果」）。そのKeyVoiceが、このモデルをダウンロードして使うようになった。KeyVoiceの作者からも、精度はかなり上がると聞いている
- 今の精度に大きな不満は無い。気にしていたのは「OSの認識ならOSを上げるだけで良くなるが、自前のモデルだと自分で最新を追いかける手入れが要るのでは」という点。これには、**版を決めて追いかけない**と決めて答えた。入れたモデルは、新しい版を追わなくても今の精度のまま悪くならない。新しい版は、気になったとき（KeyVoiceの作者が新しい版を出した、など）だけ比べて入れ替える
- OSの認識は消さずに、Haasが使えないときの予備として残す

**結論（2026-11-20）: 乗り換えない。** 自分の声の6本で比べると、辞書ありの違いがOS 9・Haas 21で、「常用版に出す基準」を満たさなかった（ログ > 試したこと）。実装・比べる仕組み・サンプルは`haas`ブランチに残し、mainには入れない。Haasの新しい版が出たとき・macOSを上げたときに`mise run compare`で比べ直す

### 調べてわかっていること（2026-11-20）

- モデルの中身: encoder 594,906,238 B（INT8）、decoder 17 MB、joint_enc 2.6 MB、joint 7.9 MB、`vocab.json`（3,072語）、`frontend.json`（前処理・窓分け・デコードの定数）、`window.f32`、`mel_filter.f32`。合計約623MB。Hugging FaceのAPI（`/api/models/okayuji/Haas-ja-v1.0-CoreML-INT8/tree/<版>?recursive=true`）では、LFSのファイル（weight.bin・model.mlmodel・`mel_filter.f32`）にだけsha256（`lfs.oid`）が出る。小さなファイル（`vocab.json`・`frontend.json`・`Manifest.json`など）はgitのblobのsha1（`oid`）だけ
- 推論コードは付いていない。前処理（プリエンファシス0.97・n_fft 512・窓400・hop 160・128メル）・15.04秒（1,504メルフレーム）ごとの窓分け（内側の端で208フレームずつ捨ててつなぐ）・TDTのgreedyデコード（1フレームに最大10記号）・SentencePieceの文字への戻しが要る。Sanami版のSwiftがこれをすべて持つ（M1で、33本中33本がPython版のCore MLと一致したと書いてある）
- 公開されている数字（M5 Max・macOS 27.2.1での計測）: 4.57秒の発話で31ms（続けて認識したとき）/116ms（20秒以上空けた初回）。28.2秒の発話で103ms/196ms。マシンで初めて読み込むときは約10秒（Neural Engineの準備）、以後は0.16秒。使っている間はメモリが+672MiBで、20秒使わないとNeural Engineの分は抜ける
- 今のOSの認識の待ち時間: 離してから確定まで103〜202ms（前のplanのPhase 1）
- 手元のMacはどれもApple Siliconでメモリ32GB以上。メモリは問題にしない。貸与PCに自分のiCloudが入っていなければ、そこではOSの認識の予備で動く
- 元のモデルにある「カスタム語彙」（認識中に語を優先させる）はNVIDIAのGPU向けの実装で、Core ML版には無い。今回は扱わない
- 元のモデルの説明より: フィラーは省きがち。漢字・かな・数字の使い分けは学習データに従う。英語の製品名がカタカナで出る誤り（今の辞書の大半）は、Haasでも残ると見ている
- 今のコードで変える場所: `Sources/App/Transcriber.swift`（OSの認識）、`DictationController.swift`（`makeSession`が無いと録音を断る → `recorder.start(format: session.format, …)` → `session.finish()`）、`Recorder.swift`（入力をセッションの形式に変換して音声スレッドから渡す。`stop()`は止める処理をキューに積むだけ）、`AppDelegate.swift`の`--transcribe-file`のフック、`MenuBarController.swift`（認識の状態を出している）
- セッション（`CLAUDECODE`）からの`mise run build`はどのMacでもad-hoc署名になる（CLAUDE.md）。署名済みのアプリでの確認は人間がする

## ログ
### 試したこと・わかったこと
- Phase 0（2026-11-20, mini M6・macOS 27.0.1）: okayuji版の18ファイルを、Hugging FaceのAPIの値（LFSはsha256、ほかはgitのblobのsha1）と突き合わせて一致。`scripts/place-haas-model.py`でiCloud Driveに置いた。miniはディスクの空きが少なく（約21GB）、iCloudが小さいファイルを置いた直後に手元から消した（`ls -lO`で`dataless`）。パッケージ（`.mlpackage`）はフォルダ単位で状態を持ち、中のファイルには状態が無い
- 基準: Sanamiの`haas-cli`をokayuji版のファイルに合わせて動かし、`say -v Kyoko`の3本（4.3秒・7.0秒・25.8秒。25.8秒は窓2つ）を16kHzのWAVにして通した。Pechaのフックの`RAW`と3本とも文字列が一致
- 時間: マシンで初めて（またはコンパイル済みの置き場が変わって）読み込むときはNeural Engineの準備で78〜82秒（公開されている数字は約10秒）。手元のコンパイル済みからは72〜124ms。コンパイルは160〜180ms、約6億バイトのsha256は250ms。認識は読み込み直後の1回目で72〜117ms（4〜7秒の音声）、292ms（25.8秒）。`haas-cli`で続けて認識すると22〜65ms。`haas-cli`のpeak memory footprintは71MB（Neural Engineの分は入っていないとみられる。アプリでは測っていない）
- iCloud Driveの許可（ad-hocのPecha Dev）: 中身が手元にあるファイルを読むと「“Pecha Dev.app”が“iCloud Drive”で管理されているファイルにアクセスしようとしています」が出て、答えるまで止まる。許可がまだ無いとき、中身が手元に無いファイルを読む・`startDownloadingUbiquitousItem`を呼ぶと、確認を出さずにCode=257で断られる。`NSFileCoordinator`で取り込むと、取り込みの段階で確認が出る。アプリ自身が作ったファイルは確認なしで読み書きできた。答えはビルドが変わってもbundle idに残る（「許可しない」のあとは新しいビルドでも確認なしで断られ、`tccutil reset FileProviderDomain io.github.nyshk97.pecha.dev`で戻った）
